## 1. 최종 API 엔드포인트 및 데이터 흐름 정의

### A. API 엔드포인트 설계 (Conceptual Endpoints)

| Endpoint | HTTP Method | 설명 | 요청 파라미터 (Query/Body) | 응답 데이터 구조 |
| :--- | :--- | :--- | :--- | :--- |
| `/api/v1/policies/search` | `GET` | 특정 조건(지역, 정책 유형)을 기반으로 정책 목록 검색 | `region`, `policy_type`, `conditions` | Policy List (Filtered & Ranked) |
| `/api/v1/policies/{policy_id}` | `GET` | 특정 정책에 대한 상세 정보 조회 | `policy_id` | Full Policy Details (Metadata, Conditions, Scope) |
| `/api/v1/policies/recommend` | `GET` | 사용자 프로필(소득, 자산) 기반 맞춤 정책 추천 | `user_profile` (Income, Asset), `preferences` | Recommended Policy List |
| `/api/v1/data/seed` | `GET` | 시스템 초기 Seed 데이터셋의 일부 또는 전체 조회 (관리용) | `data_type` (e.g., 'loan_rate', 'property_tax') | Seed Data JSON |

### B. 데이터 흐름 (Request/Response) 정의

**1. 정책 검색 흐름 (`/search`)**
*   **Request:** 사용자가 `region='Seoul'`, `policy_type='LTV_Regulation'`을 요청합니다.
*   **Processing (Backend Logic):** 시스템은 데이터베이스에서 `Policy Info` 테이블과 `Conditions` 테이블을 조인하여, 해당 지역 및 정책 유형에 맞는 모든 적용 가능한 정책 세부 조건(`Conditions`)을 필터링합니다.
*   **Response:** 필터링된 정책 목록과 해당 정책의 핵심 조건(금리, DSR 등)을 반환합니다.

**2. 상세 정보 조회 흐름 (`/{policy_id}`)**
*   **Request:** 특정 정책 ID를 요청합니다.
*   **Processing (Backend Logic):** 데이터베이스에서 해당 `policy_id`에 연결된 모든 계층 정보(Metadata, Conditions, Scope)를 조회하여 통합된 JSON 객체로 구성합니다.
*   **Response:** `Full Policy Details` 객체 반환.

## 2. 데이터베이스 스키마 설계 (SQLAlchemy 기반 Conceptual Model)

데이터의 계층적 구조를 반영하고 관계형 데이터베이스의 무결성을 확보하기 위해 최소 4개의 핵심 테이블을 설계합니다.

### A. 테이블 정의 (Schema Definition)

**1. `Policy_Metadata` (정책 메타데이터)**
*   **목표:** 정책의 고유 식별자와 상위 정보를 관리합니다.
*   **필드:**
    *   `policy_id` (PK, String/UUID): 정책의 고유 식별자.
    *   `policy_type` (String): 정책 유형 (예: LTV, DSR, 금리 규제).
    *   `description` (Text): 정책에 대한 상세 설명 (Markdown 기반).
    *   `status` (String): 정책의 현재 유효 상태 (Active, Draft, Expired).
    *   `created_at` (DateTime): 생성 일시.

**2. `Policy_Conditions` (세부 조건)**
*   **목표:** 정책의 구체적인 적용 기준 및 수치를 저장합니다.
*   **필드:**
    *   `condition_id` (PK, Integer): 조건의 고유 식별자.
    *   `policy_id` (FK): 연결된 정책 메타데이터 ID.
    *   `condition_name` (String): 조건의 이름 (예: LTV_Rate, DSR_Limit).
    *   `value` (Float/Decimal): 조건의 수치 값.
    *   `unit` (String): 단위 (예: %, Ratio).

**3. `Policy_Scope` (적용 범위)**
*   **목표:** 정책이 적용되는 지리적 또는 기타 범위를 정의합니다.
*   **필드:**
    *   `scope_id` (PK, Integer): 범위의 고유 식별자.
    *   `policy_id` (FK): 연결된 정책 메타데이터 ID.
    *   `region` (String): 적용 지역 (예: 'Seoul', 'Gyeonggi-do').
    *   `jurisdiction` (String): 관할 지역.

**4. `Seed_Data` (초기 Seed 데이터셋)**
*   **목표:** 시스템 초기 학습 및 테스트를 위한 실제 시장 데이터를 저장합니다.
*   **필드:**
    *   `seed_id` (PK, Integer): Seed 데이터의 고유 식별자.
    *   `data_type` (String): 데이터 유형 (예: 'loan_rate', 'property_tax', 'interest_rate').
    *   `value` (Float/Decimal): 실제 데이터 값.
    *   `source` (String): 데이터 출처 (예: 'KDB', 'Government_API').
    *   `timestamp` (DateTime): 데이터 갱신 시점.

*   **질문 1 (매출 직접 연계):** 현재 설정된 핵심 수익화 가설(예: 특정 지역 매물 추천 성공률, 사용자 체류 시간)을 **측정하기 위해** 데이터셋 중 **반드시 포함되어야 하는 최소 데이터 포인트**는 무엇이며, 해당 데이터의 접근 권한은 어떻게 설정되어야 합니까?
*   **질문 2 (MVP 우선순위 연계):** MVP 기능 중 **가장 먼저 검증해야 할** 기능(예: 지역별 가격 비교, 실시간 동향 분석)을 구현하기 위해, 현재 보유한 데이터셋 중 **가장 높은 예측 정확도**를 제공하는 데이터는 무엇이며, 이를 위한 접근 권한을 어떻게 확보해야 합니까?
*   **질문 3 (리스크/보안 연계):** 데이터 접근 권한을 확장할 경우, **보안 및 개인정보 보호(GDPR/국내 법규 준수)** 측면에서 가장 민감한 데이터는 무엇이며, 이 데이터에 대한 접근 권한을 부여하는 데 필요한 **최소한의 접근 수준(Read/Write)**은 무엇입니까?

*   **질문 4 (시간 효율성):** 특정 데이터 접근 권한을 확보하는 데 필요한 **행정적/기술적 절차**를 완료하는 데 예상되는 **최소 소요 시간**은 얼마이며, 이 시간을 MVP 기능 개발 일정에 어떻게 통합해야 할까요?
*   **질문 5 (데이터 품질 연계):** 데이터 마이그레이션 과정에서 데이터의 **정확성(Data Quality)**이 KPI 달성에 미치는 영향을 고려할 때, 데이터 정제(Cleaning) 작업에 필요한 **추가 리소스(인력 또는 시간)**를 개발팀이 어떻게 산정하고 반영할 예정입니까?

## 📊 핵심 KPI 기반 데이터 범위 및 권한 수준 제안 (개발팀 논의 준비)

개발팀과의 논의를 위한 핵심 제안 프레임워크를 아래와 같이 제시합니다. 이 제안은 '수익화 모델 1개 가설 검증 및 매출화'라는 장기 목표에 직접적으로 연계되어, 기술적 요구사항을 비즈니스 목표에 기반하여 재정의하는 기반이 됩니다.

### 1. 핵심 KPI 정의 (KPI Alignment)

기술적 요구사항을 정의하기 전에, 개발팀이 달성해야 할 핵심 KPI를 명확히 정의하여 데이터 요청의 우선순위를 설정합니다.

| 비즈니스 목표 | 핵심 KPI (Metric) | 데이터 요구사항 (Data Dependency) | 측정 주기 |
| :--- | :--- | :--- | :--- |
| **수익화 가설 검증** | **활성 사용자 수 (MAU/DAU)** | 사용자 등록, 로그인, 세션 데이터 | 일/주 |
| **수익화 가설 검증** | **체류 시간 (Session Duration)** | 앱 내 핵심 기능(부동산 정보) 조회 및 탐색 데이터 | 세션 단위 |
| **수익화 가설 검증** | **핵심 행동 전환율 (Conversion Rate)** | 특정 부동산 정보 조회 후, 광고/서비스 연결 클릭률 | 일/주 |
| **서비스 품질** | **데이터 정확도 (Data Accuracy)** | 부동산 데이터의 최신성 및 정합성 (외부 소스 연계) | 실시간/일 |

### 2. 데이터 범위 및 권한 수준 제안 (Scope & Permission Level)

위 KPI 달성을 위해 요구되는 데이터의 최소 범위와 필요한 접근 권한 수준을 다음과 같이 제안합니다.

#### A. 필수 데이터 범위 (Minimum Viable Scope)

**목표:** MVP 기능(부동산 추천)의 핵심 가치를 측정하고 수익화 가설을 검증하는 데 필요한 데이터에 한정합니다.

1.  **사용자 행동 데이터 (User Behavior Data):**
    *   **포함:** 사용자 등록/로그인 정보, 앱 세션 기록, 핵심 추천 기능(부동산 목록, 상세 정보) 조회 기록.
    *   **제외:** 민감한 개인 식별 정보(PII)는 최소화하고, 행동 패턴 분석에 필요한 집계 데이터만 요청합니다.
2.  **부동산 데이터 연계 데이터 (Property Data Linkage):**
    *   **포함:** 추천 알고리즘 학습에 필요한 부동산 데이터의 **특정 필드** (예: 지역, 가격대, 면적, 거래 기록 요약).
    *   **제외:** 모든 상세 거래 기록이나 외부 데이터 소스에 대한 무제한 접근 권한은 MVP 단계에서는 제외합니다.

#### B. 권한 수준 제안 (Permission Level)

**목표:** 데이터 보안을 유지하면서 개발 속도를 확보하기 위해 최소 권한 원칙(Principle of Least Privilege)을 적용합니다.

1.  **데이터 접근 권한:**
    *   **제안:** **읽기 전용(Read-Only)** 접근 권한을 기본으로 설정합니다. 데이터 수정 권한은 특정 관리자 계정으로 제한합니다.
    *   **근거:** MVP 단계에서는 데이터의 무결성을 보장하는 것이 데이터의 양보다 중요합니다.
2.  **API 엔드포인트 접근 권한:**
    *   **제안:** 핵심 KPI 산출에 직접적으로 필요한 데이터만 조회할 수 있는 **특화된 API 엔드포인트**에 대한 접근 권한만 부여합니다. 전체 데이터베이스에 대한 접근은 별도의 보안 검토 후 진행합니다.
    *   **근거:** 데이터 요청의 효율성과 개발 일정 연계성을 극대화하기 위해 KPI 기반으로 논의를 진행합니다.

### 3. 기술 요구사항 재정의 준비 (Next Step Preparation)

위의 제안을 바탕으로, 개발팀에게 전달할 기술 요구사항은 다음과 같이 재정의될 준비를 합니다.

*   **기존 요구사항:** "부동산 추천 기능을 구현하라."
*   **재정의된 요구사항 (KPI 기반):** "사용자 행동 데이터를 기반으로, 특정 지역/가격대 부동산 목록을 제공하고, 사용자의 탐색 행동에 따라 추천 알고리즘의 정확도를 측정할 수 있는 최소한의 데이터 구조 및 API를 구현하라."

2.  **부동산 데이터 연계 데이터:**
    *   **제약:** 부동산 데이터는 외부 소스(API 또는 크롤링)에서 가져와 내부 DB에 **정규화(Normalization)**해야 합니다. 단순 조회용 필드만 내부 모델에 매핑하고, 모든 원본 데이터는 별도의 데이터 레이크 또는 원천 시스템에 보관해야 합니다.
    *   **DB 제약:** 부동산 데이터와 사용자 행동 데이터를 효과적으로 연결하기 위해, **지역 코드(Geo-ID) 기반의 관계형 테이블 구조**를 설계해야 합니다.

#### B. 권한 수준 (Principle of Least Privilege) 관련 제약

1.  **보안 아키텍처 제약:**
    *   **제약:** 데이터 접근 권한은 **Role-Based Access Control (RBAC)** 기반으로 구현해야 합니다. 특정 API 엔드포인트는 특정 역할(예: 분석가, 사용자)만 접근 가능하도록 **미들웨어 레벨에서 엄격하게 통제**해야 합니다.
    *   **API 보안:** 모든 데이터 요청은 **OAuth 2.0 또는 JWT 기반 인증**을 필수로 하며, 데이터 요청 시에는 요청된 데이터의 민감도에 따라 접근 권한을 동적으로 부여해야 합니다.

### 1. 테이블 정의 (Table Definitions)

#### 1.1. `regions` (지역 정보)
지역 코드를 기준으로 모든 부동산 데이터를 정렬하고 필터링하기 위한 마스터 테이블입니다.

| 필드명 (Field Name) | 데이터 타입 (Data Type) | 제약 조건 (Constraint) | 설명 (Description) |
| :--- | :--- | :--- | :--- |
| `region_id` | INT | PRIMARY KEY | 지역 고유 ID |
| `region_code` | VARCHAR(10) | UNIQUE, NOT NULL | 지역 코드 (예: 서울, 부산) |
| `latitude` | DECIMAL(9,6) | NOT NULL | 위도 정보 |
| `longitude` | DECIMAL(9,6) | NOT NULL | 경도 정보 |
| `region_name` | VARCHAR(50) | NOT NULL | 지역 이름 |
| `market_status` | ENUM | NOT NULL | 시장 상태 (예: 안정, 상승, 하락) |

#### 1.2. `properties` (부동산 매물 정보)
실제 판매 중이거나 등록된 부동산 매물 정보를 저장합니다.

| 필드명 (Field Name) | 데이터 타입 (Data Type) | 제약 조건 (Constraint) | 설명 (Description) |

| `region_id` | INT | FOREIGN KEY (regions) | 해당 매물이 속한 지역 ID |
| `address` | VARCHAR(255) | NOT NULL | 상세 주소 |
| `property_type` | ENUM | NOT NULL | 부동산 유형 (예: 아파트, 빌라, 오피스텔) |

| `size_sqm` | INT | NOT NULL | 면적 (제곱미터) |
| `listing_date` | TIMESTAMP | NOT NULL | 등록일 |
| `status` | ENUM | NOT NULL | 매물 상태 (예: 등록됨, 판매중, 거래완료) |
| `property_details` | JSONB | NULL | 상세 정보 (추후 확장용) |

부동산 거래 이력 데이터를 기록하여 시장 동향 분석의 기반을 마련합니다.

| :--- | :--- | :--- | :--- |
| `transaction_id` | BIGINT | PRIMARY KEY | 거래 고유 ID |
| `property_id` | BIGINT | FOREIGN KEY (properties) | 거래된 매물 ID |
| `buyer_id` | BIGINT | FOREIGN KEY (users) | 구매자 ID |
| `seller_id` | BIGINT | FOREIGN KEY (users) | 판매자 ID |
| `transaction_date` | DATE | NOT NULL | 거래 날짜 |
| `sale_price` | BIGINT | NOT NULL | 실제 거래 가격 |
| `transaction_type` | ENUM | NOT NULL | 거래 유형 (예: 매매, 전세) |

#### 1.4. `users` (사용자 정보)
앱 사용자의 기본 정보를 저장합니다.

| 필드명 (Field Name) | 데이터 타입 (Data Type) | 제약 조건 (Constraint) | 설명 (Description) |

## 부동산 추천 앱 MVP: 데이터 범위 및 권한 최종 확정 및 기술 요구사항 정리

본 문서는 부동산 추천 앱 MVP의 핵심 KPI 달성을 위해 필요한 데이터 범위(Scope)와 권한 수준을 최종 확정하고, 이를 기반으로 개발팀에 전달할 기술적 요구사항의 핵심 논점을 정리합니다.

### 1. 핵심 KPI 기반 데이터 범위(Scope) 정의

MVP의 핵심 목표는 **"부동산 추천을 통한 사용자 만족도 증대 및 잠재적 수익화 기반 마련"**입니다. 이를 달성하기 위해 필요한 데이터 범위는 최소화하되, 추천 알고리즘의 정확도와 사용자 경험을 보장하는 데 필수적인 데이터에 한정합니다.

| MVP 기능 목표 | 필수 데이터 범위 (Scope) | 상세 데이터 항목 (예시) | 비고 (KPI 연계) |
| :--- | :--- | :--- | :--- |
| **지역 기반 추천** | 지역별 기본 정보 (필수) | 시/도, 구/군, 동, 평균 시세 데이터 | 지역별 경쟁 우위 분석 |
| **부동산 상세 정보** | 매물 기본 정보 | 주소, 면적(평수), 층수, 방/채 수, 거래 시점 | 추천 정확도 및 사용자 만족도 |
| **시장 동향 반영** | 시세 및 거래 데이터 | 최근 3개월/6개월 평균 거래가, 매물 수 | 시장 분석 기능 제공 |
| **사용자 피드백** | 사용자 리뷰/평점 | 사용자 리뷰 텍스트, 평점 점수 | 서비스 신뢰도 및 재방문율 |

**결론:** MVP 단계에서는 **'정확한 지역별 시세 데이터'**와 **'매물 기본 정보'**에 집중해야 하며, 민감하거나 비공개적인 상세 거래 정보는 초기 단계에서는 제외하여 데이터 요청의 복잡성과 보안 리스크를 최소화합니다.

### 2. 권한 수준(Permission Level) 최종 확정

데이터 접근 권한은 **'최소 권한의 원칙(Principle of Least Privilege)'**에 따라 정의하여 개발 효율성과 보안을 동시에 확보합니다.

*   **데이터 접근 수준:** **읽기 전용 (Read-Only)** 접근만을 허용합니다. (쓰기/수정 권한은 MVP 이후 단계에서 별도 승인 필요)
*   **데이터 범위:** **지역 코드 기반**으로 데이터 요청을 설계합니다. (DB 스키마 설계에 따라 지역 코드를 기준으로 데이터 접근을 제한)
*   **보안 고려사항:** 모든 데이터 요청은 API 게이트웨이를 통해 이루어지며, 데이터 요청 시에는 **KPI 달성에 직접적으로 기여하는 최소한의 필드만** 요청하도록 제한합니다.

### 3. 개발팀 전달을 위한 핵심 논점 (Key Discussion Points)

1.  **KPI 연계성 강조:** "우리의 데이터 요청은 단순한 정보 수집이 아니라, **핵심 KPI(예: 추천 정확도, 사용자 참여율) 달성**을 위한 필수적인 입력값임을 명확히 인지해야 합니다."
2.  **데이터 범위의 명확화:** "MVP 단계에서는 **지역 코드, 면적, 기본 가격** 등 핵심 필드에 대한 접근을 우선적으로 요구하며, 상세 거래 기록과 같은 민감 데이터는 추후 단계에서 추가 논의를 통해 접근 권한을 확대할 계획입니다."

## 부동산 추천 앱 MVP 데이터베이스 스키마 및 기술 실현 가능성 검토 보고서

### 1. 데이터베이스 스키마 (DB Schema) 초안 검토

**검토 결과:** 제안된 데이터 범위(지역 코드, 매물 기본 정보, 시세 데이터, 사용자 피드백)는 MVP 목표(지역 기반 추천 및 기본 정보 제공)를 달성하기에 **충분하며 논리적**입니다. 핵심은 데이터 간의 관계 설정과 지역 코드 기반의 접근 제어에 있습니다.

| 테이블/엔티티 | 핵심 필드 | 관계 및 검토 사항 | 기술적 실현 가능성 |
| :--- | :--- | :--- | :--- |
| **Regions (지역)** | `region_id` (PK), `city`, `province`, `district`, `region_code` (FK) | 모든 데이터의 최상위 식별자로 사용됨. 지역 코드 기반 접근 제어의 핵심. | **높음** (정규화 용이) |
| **Properties (매물)** | `property_id` (PK), `region_id` (FK), `address`, `area_sqm`, `floor`, `room_count`, `listing_date` | 지역과 1:N 관계. 추천 알고리즘의 핵심 입력값. | **높음** (표준화된 GIS/주소 API 연동 필요) |
| **MarketData (시장 데이터)** | `market_id` (PK), `region_id` (FK), `avg_price_3m`, `avg_price_6m`, `listing_count` | 지역별 시장 동향 제공. 추천 정확도에 직접 기여. | **중간** (외부 시세 API 연동 및 데이터 정제 필요) |
| **Reviews (사용자 피드백)** | `review_id` (PK), `property_id` (FK), `user_id` (FK), `rating`, `comment` | 사용자 만족도 측정. 추천 알고리즘의 보조 입력값. | **높음** (관계 설정 용이) |

### 2. API 및 데이터 파이프라인 제약 사항

**제약 사항:**

1.  **지역 코드 기반 접근 제어 (Security & API):**
    *   **제약:** 모든 API 엔드포인트는 반드시 `region_code`를 파라미터로 요구해야 하며, 이 코드가 데이터베이스 접근의 **최우선 보안 필터**로 작동해야 합니다.
    *   **실현 방안:** API 게이트웨이 레벨에서 사용자 인증 정보와 요청된 `region_code`를 매칭하여, 해당 코드가 허용된 범위 내에 있는지 실시간으로 검증해야 합니다.
2.  **데이터 동기화 (Data Pipeline):**
    *   **제약:** `MarketData` 테이블은 실시간성이 중요하므로, 외부 부동산 API 또는 크롤링 시스템과의 **안정적인 데이터 파이프라인** 구축이 선행되어야 합니다. 수동 업데이트는 금지합니다.
    *   **실현 방안:** 외부 소스(예: 공공 데이터 포털, 상업용 부동산 API)에서 데이터를 가져와 ETL(Extract, Transform, Load) 프로세스를 통해 DB에 정기적으로 반영하는 자동화 스크립트(Python/Airflow)를 구축해야 합니다.
3.  **데이터 범위 제한 (Scope Limitation):**
    *   **제약:** MVP 단계에서는 민감한 개인 거래 정보(실제 매매 가격, 개인 연락처 등)는 **DB에 저장하지 않거나, 암호화하여 별도의 보안 레이어**에 분리해야 합니다. 저장되는 데이터는 **추천 알고리즘에 필요한 집계된 통계 데이터**로 제한해야 합니다.

### 3. 기술적 실현 가능성 요약

| **API 통합** | 중간 | 외부 시세 데이터의 안정적인 확보 및 실시간 업데이트를 위한 외부 API 의존성이 높음. |
| **보안** | 높음 | 최소 권한 원칙을 DB 접근 및 API 응답에 강력하게 적용할 경우, 데이터 유출 위험을 최소화할 수 있음. |
