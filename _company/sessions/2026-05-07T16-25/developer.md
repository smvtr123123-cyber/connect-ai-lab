## 📊 데이터 요청의 기술적 실현 가능성 및 제약 사항 검토

`Business` 에이전트가 제안한 핵심 KPI 기반 데이터 범위 및 권한 수준에 대해 DB, API, 보안 관점에서 기술적 실현 가능성과 제약 사항을 다음과 같이 정리합니다.

### 1. 핵심 KPI 및 데이터 요구사항에 대한 기술 검토

| KPI / 데이터 요구사항 | 기술적 실현 가능성 | 주요 기술 제약 사항 |
| :--- | :--- | :--- |
| **활성 사용자 수 (MAU/DAU)** | **높음** | 사용자 세션 및 로그인 기록을 별도 로그 테이블에 저장하고, 실시간 집계를 위한 Redis 또는 별도 분석 DB 연동 필요. |
| **체류 시간 (Session Duration)** | **중간** | 세션 시작/종료 타임스탬프를 기록하고, 특정 부동산 정보 조회 시점과 종료 시점을 정확히 측정하는 로직 구현 필요. |
| **핵심 행동 전환율 (Conversion Rate)** | **높음** | 특정 행동(예: 부동산 상세 조회 후 클릭)을 이벤트 로그로 기록하고, 이를 기반으로 A/B 테스트 또는 퍼널 분석 로직을 구현해야 함. |
| **데이터 정확도 (Data Accuracy)** | **낮음 (외부 연계)** | 외부 부동산 데이터 소스(API)의 실시간/정합성 검증은 데이터 파이프라인(ETL)의 복잡성을 크게 증가시킴. 데이터 정합성 확보를 위한 크롤링/API 연동 안정화가 선행되어야 함. |

### 2. 데이터 범위 및 권한 수준에 대한 기술 제약 사항

#### A. 필수 데이터 범위 (Minimum Viable Scope) 관련 제약

1.  **사용자 행동 데이터:**
    *   **제약:** PII(개인 식별 정보)를 직접적으로 저장하는 대신, 사용자 ID를 해시 처리하고, 행동 로그는 비식별화된 집계 형태로 저장해야 합니다. 이는 데이터베이스 설계 시 **분리 저장(Separation)** 전략을 요구합니다.
    *   **API 제약:** 사용자 행동 API는 집계 요청에 최적화되어야 하며, 개별 사용자의 민감한 행동 기록에 대한 직접 접근은 엄격히 차단해야 합니다.

2.  **부동산 데이터 연계 데이터:**
    *   **제약:** 부동산 데이터는 외부 소스(API 또는 크롤링)에서 가져와 내부 DB에 **정규화(Normalization)**해야 합니다. 단순 조회용 필드만 내부 모델에 매핑하고, 모든 원본 데이터는 별도의 데이터 레이크 또는 원천 시스템에 보관해야 합니다.
    *   **DB 제약:** 부동산 데이터와 사용자 행동 데이터를 효과적으로 연결하기 위해, **지역 코드(Geo-ID) 기반의 관계형 테이블 구조**를 설계해야 합니다.

#### B. 권한 수준 (Principle of Least Privilege) 관련 제약

1.  **보안 아키텍처 제약:**
    *   **제약:** 데이터 접근 권한은 **Role-Based Access Control (RBAC)** 기반으로 구현해야 합니다. 특정 API 엔드포인트는 특정 역할(예: 분석가, 사용자)만 접근 가능하도록 **미들웨어 레벨에서 엄격하게 통제**해야 합니다.
    *   **API 보안:** 모든 데이터 요청은 **OAuth 2.0 또는 JWT 기반 인증**을 필수로 하며, 데이터 요청 시에는 요청된 데이터의 민감도에 따라 접근 권한을 동적으로 부여해야 합니다.

### 3. 최종 기술 요구사항 요약 (Actionable Items)

데이터 요청을 성공적으로 수행하기 위해 다음의 기술적 기반 작업이 선행되어야 합니다.

1.  **DB 스키마 확정:** 사용자 행동 로그 테이블과 부동산 데이터 테이블 간의 **정규화된 조인(Join) 구조**를 설계합니다. (개발팀 협의 필요)
2.  **API 설계:** 모든 데이터 요청은 **KPI 측정에 최적화된 집계 쿼리**를 반환하도록 API 엔드포인트를 설계합니다.
3.  **보안 레이어 구축:** 모든 데이터 요청에 대해 **RBAC 정책을 적용**하는 인증/인가 계층을 개발합니다.
